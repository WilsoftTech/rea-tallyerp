## Phase 5 design and dependency admission — before installation

Next.js **16.4.3** is the current stable release confirmed by official docs and npm metadata; MIT, Node >=20.9, compatible with existing React/ReactDOM 19.3.1 and Node 24. Reuse those existing versions/types, native IndexedDB/Web Crypto/Cache APIs, the current CSS/forms and installed Vite/Playwright. No IndexedDB wrapper, worker/PWA package, state library, UI framework or auth provider is needed. Next supplies only its required declared server/build dependencies. Browser test binaries may be downloaded under ignored workspace cache only when an installed browser cannot provide the required matrix. Bundle/advisory/resource effects remain unverified until actual install/build/test.

Original proposed architecture: move reusable desktop UI, styling and CAS orchestration into a host-neutral workspace, retaining the native host. Browser storage uses actual IndexedDB read/write transactions with strict durability where supported; grants/crypto/network run outside those transactions, with revision/generation/profile checks repeated inside. A public static Next shell hydrates all accounting locally; no company state or credential is server-rendered. A bounded same-origin proxy forwards only protocol routes to an operator-configured upstream, with no user-selected upstream/redirects or browser database credentials. Auth/company responses are never cached.

Proposed worker policy: precache a generated public-shell/hashed-asset allowlist, never APIs or mutations; normal waiting-worker lifecycle, no forced skipWaiting while other tabs may have unsaved work. IndexedDB closes connections on versionchange and exposes blocked/newer-schema outcomes without resetting stores. Browser sessions/bearers stay in memory; source data/public grants persist. Encrypted external backups use maintained Web Crypto PBKDF2/AES-GCM; browser storage is plaintext/best effort and private/evicted storage cannot be promised durable. Restores preserve command IDs, rotate local generation and require online reconciliation for synchronized books. The existing 24-hour maximum grant is reused; no financial last-write-wins.

These are active-phase design choices, not yet implemented/verified browser features. No uncertainty in reference behavior requires a manual walkthrough. Phase 6 remains unauthorized.

## Dependency admission

Phase 4 admission before installation: use Node's HTTP/fetch/crypto/scrypt for a small authenticated API (no Express, auth provider or extra queue required). Prisma stable 7 and its PostgreSQL pg adapter/driver supply cloud database access; Zod validates bounded versioned external envelopes in a shared contracts package, while the pure domain stays framework-independent. Existing TS/Vitest/Playwright/native tooling is reused. A portable official PostgreSQL binary and isolated loopback test cluster are necessary because no existing PostgreSQL/container runtime was found; no system service or external hosting is needed. Native HTTPS transport and Ed25519 grant verification require maintained Rust libraries; cloud bearer tokens stay in native memory, signed offline permissions contain no secret and are revalidated/expired. No refresh secret is stored in renderer storage or plaintext SQLite. Selected npm pins: Prisma/client/adapter-pg 7.10.1 (Apache-2.0), pg 8.23.1 and Zod 4.6.7 (MIT), @types/pg 8.23.1 for development. Native lock pins reqwest 0.13.5, ed25519-dalek 3.0.0 and base64 0.23.1 for HTTPS/signature/encoding; official platform APIs are reused. Final graph/advisory/build/size results are recorded in phase evidence.

Phase 4 original sync implementation: explicit enrollment validates/reconciles a local-only snapshot before importing into a scoped cloud company; local journals stay immutable and cloud canonical history is stored separately. New receipts retain typed commands for a versioned outbox. PostgreSQL transactions lock a company and atomically persist command outcome, accepted journal/audit and gap-free company cursor; permission, lock, dependency and altered-payload conflicts are explicit. Incremental bounded pull applies canonical snapshot/cursor/outcomes atomically. Backups preserve IDs but rotate device generation; reconnection reconciles receipts before resuming, never generates new financial IDs. The owner explicitly selected **24-hour offline posting grants**; shorter durations are used only by synthetic expiry tests. No phase gate is waived.

Native TLS selection: the initial bundled Rust TLS provider failed to compile on this Windows compiler. Reqwest now uses the Windows TLS/certificate implementation through native-tls, without installing another TLS build toolchain. Ed25519-dalek verifies signed public offline grants, and base64 reuses the existing encoding dependency. Tokens stay in native memory. Direct licenses: reqwest/base64 MIT OR Apache-2.0; ed25519-dalek BSD-3-Clause, confirmed from pinned Cargo manifests. The actual Windows build and scoped advisory checks are recorded in phase evidence; no non-Windows support is claimed.

## Risks and decisions requiring owner input

Phase 5 implementation follows the pre-install admission above: Next.js 16.4.3 is the sole new runtime framework (MIT; existing React/TypeScript/Vite/Playwright reused). Native IndexedDB, BroadcastChannel, Service Worker/Cache and Web Crypto APIs proved sufficient; no wrapper/PWA/auth/state/crypto/UI catalog dependencies were needed. Existing UI/styles/CAS adapter now reside in populated `packages/workspace`; accounting remains in pure domain/application packages. Browser-only Web Crypto uses PBKDF2-HMAC-SHA256 600,000/AES-256-GCM for credential verification and ERPWEB01 external backups, rather than adding a WASM Argon2 bundle. This does not encrypt IndexedDB. Actual resource/security/check results must be read from current phase evidence, not this admission record.

The browser is served by a public static Next client route plus a fixed-origin accounting proxy; it contains no Node/PostgreSQL credentials and requires no Next server after successful offline-shell installation for local-only work. The production worker is generated from build-hashed public assets, follows normal waiting, never invokes skipWaiting and never stores API/RSC/accounting payloads. All old workspace tabs must close for an update. Native/browser backup formats deliberately differ; cloud sync shares the common accounting model. Requesting storage persistence and external encrypted backups is mandatory UX, with best-effort/plaintext/private-window/eviction limits disclosed.

Phase 5 integration corrections retain phase boundaries: reviewed enrollment retries now return a current canonical epoch/cursor alongside the original import identity; scope-only ledger/group UI inputs satisfy strict wire contracts; known revocation outcomes pause browser/native authority atomically. No SQL migration, invoice, stock, deployment, new identity provider or later-phase business feature was introduced.

These owners are proposed responsibilities, not assigned people. Unresolved future decisions do not justify implementing out of phase.

## Technical research used

Sources consulted on 2026-10-25. These establish platform constraints, not our implementation or Tally behavior.

- [Tauri Next.js integration](https://v2.tauri.app/start/frontend/nextjs/) requires static export for that integration; separate React desktop host is our architectural choice.
- [Tauri security model](https://v2.tauri.app/security/) describes the WebView/native trust boundary; specific IPC constraints are our requirements.
- [SQLite synchronous settings](https://www.sqlite.org/pragma.html#pragma_synchronous) describe WAL FULL versus NORMAL durability; planned settings must be read back and fault-tested.
- [SQLite online backup](https://www.sqlite.org/backup.html) provides a consistent backup mechanism; encryption and restore workflow are our design work.
- [Browser storage quotas/eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) documents storage loss and persistence limits; we cannot guarantee retention.
- [PostgreSQL row security](https://www.postgresql.org/docs/18/ddl-rowsecurity.html) documents default-deny and owner/BYPASSRLS behavior; our runtime role must not bypass it.

No jurisdictional legal/compliance advice is inferred from these technical sources. Uganda statutory research belongs to its approved phase.
